A compiler is automata theory that had to ship.

Every idea in formal language theory shows up inside a compiler doing a job. A finite automaton becomes the scanner. A pushdown automaton becomes the parser. The Chomsky hierarchy becomes the reason those two are separate programs. Compilearn puts both halves on one page: the six phases of a working compiler you can type into, and the machines underneath them — regular expressions turned into NFAs, NFAs determinised and minimised, grammars turned into LL(1), LR(0), SLR(1), LALR(1) and CLR(1) tables, every construction computed live from what you enter.

01

The shape of the whole machine

Six phases in a line, split into a front end that understands the source language and a back end that speaks the target machine. Two components sit outside the line because every phase talks to them: the symbol table, which remembers what each name means, and the error reporter, which has to describe a failure in terms of the line you wrote rather than the structure it was working on.

The split matters commercially. Because the front end ends at a machine-independent intermediate representation, one front end plus n back ends covers n processors, and m front ends plus one back end covers m languages — rather than m×n separate compilers. It is the reason LLVM, GCC and the JVM are organised the way they are.

04

Which languages a compiler can accept

“Accepting a language” means deciding whether a string belongs to an infinite set defined by rules. A compiler does not do this once — it does it three times, at three different levels of power, because each level is the weakest tool that can still do its job. Weakest is a virtue: the weaker the machine, the faster it runs and the better the error messages. The two labs below let you build the machines for the top two rungs yourself.

Read the table as a staircase a compiler climbs only as far as it must. The scanner refuses to use a stack, so it cannot see nesting — it hands the parser a flat list. The parser owns a stack but refuses to remember anything about names, so x + 1 parses perfectly even when x was never declared. Only the semantic phase keeps a table of facts that persists across the whole tree, and that table is precisely the “context” the middle rung is named after.

In practice nobody implements a context-sensitive grammar. The rule “every identifier must be declared” can be written as one, but the grammar is unusable — so compilers carve off the context-free skeleton, parse that with a pushdown automaton, and check the rest by walking the resulting tree with a symbol table in hand. That division of labour is the single most important design decision in the front end.

05

Regular languages: patterns, and the machines they compile to

Everything a scanner recognises is a regular language, and there are four equivalent ways to write one down: a regular expression, an NFA, a DFA, and the unique smallest DFA. Each form converts mechanically into the next, and those conversions are what a lexer generator such as lex or flex runs when you hand it a .l file. Start with the automaton the compiler above actually uses, then build your own from a pattern.

Try 2count. The machine dies on the second character — not because the name is meaningless, but because no arrow leaves the number state on a letter. That is the whole of “lexical error”.

Build one yourself: a pattern, compiled to three machines

Write a regular expression and watch Thompson's construction turn it into an NFA with ε-moves, the subset construction turn that NFA into a DFA, and partition refinement collapse the DFA to the unique minimal one. Operators: | alternation, juxtaposition for concatenation, * zero or more, + one or more, ? optional, parentheses for grouping. Every other character is a literal symbol.

The three machines accept exactly the same set of strings and differ only in cost. The NFA is small and built in time proportional to the pattern, but simulating it means tracking a set of states at once. The DFA tracks a single state and so runs in one table lookup per character, but can be exponentially larger in the worst case. The minimal DFA is the unique smallest machine for the language — unique up to renaming states, which is why two patterns are equivalent exactly when their minimal DFAs are identical.

Context-free languages: one grammar, five parsers

A grammar on its own says nothing about how hard it is to parse. What matters is whether a deterministic machine can decide, from a bounded amount of information, which rule to apply next. Each parsing method answers that differently, and each one accepts a different set of grammars. Notice what the LR tabs are actually showing you: a finite automaton. Its states are sets of items — productions with a dot marking how much has been seen — and it recognises the language of viable prefixes, the stack contents that could still lead to a successful parse. That automaton is regular even though the language being parsed is not. The stack supplies the extra power; the automaton only decides what to do with it.

07

Which parser for which grammar

These classes nest. Every LR(0) grammar is SLR(1), every SLR(1) grammar is LALR(1), every LALR(1) grammar is CLR(1). LL(1) sits off to the side: it overlaps the LR classes without being contained in any of them, because top-down and bottom-up fail on different things.

In practice the middle of that picture wins. LALR(1) has the table size of SLR(1) and close to the grammar coverage of CLR(1), which is why yacc and bison generate LALR(1) parsers and why so many language grammars are written to stay inside it. Recursive descent — hand-written LL — survives for the opposite reason: the tables are invisible, the code is ordinary functions, and error messages come out in the shape of the language instead of the shape of a state machine.
